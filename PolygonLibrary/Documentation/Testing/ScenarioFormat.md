# Scenario Format

Это эталонный формат для документов в `Documentation/Testing/CoveragePlan/`.

## Когда использовать

- один класс или одна небольшая сущность получает отдельную папку;
- в папке есть `Index.md`;
- сценарии раскладываются по нескольким тематическим файлам, если класс не совсем маленький.

Формат подходит и для больших классов, если:

- не делать один огромный файл на весь класс;
- делить по смысловым зонам API:
  - `Construction`
  - `Queries`
  - `Operators`
  - `Geometry`
  - `Intersection`
  - `Factories`
  - и т.д.

## Общая структура папки

```text
<ClassName>/
  Index.md
  <Topic1>.md
  <Topic2>.md
  ...
```

## Ссылки

- внутри `Documentation/Testing` используются только относительные ссылки;
- ссылки на исходники и тесты тоже пишутся относительными от текущего `.md`-файла;
- абсолютные пути вида `F:\...` в этой документации не используются.

## `Index.md`

`Index.md` должен содержать:

- что это за объект;
- какие тематические файлы существуют;
- краткую summary-таблицу по темам;
- краткое замечание о текущем покрытии.

Пример:

```md
# Line2D

## Scope

Краткое описание объекта и его роли.

## Topics

- `Construction.md` - построение и инварианты.
- `QueriesAndIntersection.md` - запросы и пересечения.

## Current Coverage Summary

| Topic | Status | Comment |
| --- | --- | --- |
| Construction | ` ` | Сценарии ещё не размечены по фактическому покрытию. |
| Queries and Intersection | ` ` | Сценарии ещё не размечены по фактическому покрытию. |
```

## Тематический файл

Каждый тематический файл должен содержать:

- `Scope`
- таблицу `Scenarios`
- `Gaps`
- `Notes`

Базовый шаблон:

```md
# <Topic>

## Scope

Кратко: что именно покрывает этот файл.

## Scenarios

| ID | Status | Scenario | Tests |
| --- | --- | --- | --- |
| `OBJ-TOPIC-001` | ` ` | Описание сценария. | |
| `OBJ-TOPIC-002` | `x` | Описание сценария. | [SomeTests.cs](../../../Tests/SharedTests/SomeTests.cs#L42) |
| `OBJ-TOPIC-003` | `~` | Описание сценария. | [SomeTests.cs](../../../Tests/SharedTests/SomeTests.cs#L57) |
| `OBJ-TOPIC-004` | `-` | Сценарий не входит в активный слой. | |

## Gaps

- Что пока отсутствует.

## Notes

- Практические замечания для будущего написания тестов.
```

## Правила для колонок таблицы

### `ID`

- должен быть коротким и стабильным;
- должен отражать объект и тему;
- должен быть уникальным в пределах класса.

Примеры:

- `L2D-CTOR-001`
- `L2D-QRY-003`
- `VEC-OP-014`
- `CPOLY-CONTAINS-006`

### `Status`

Используются значения:

- ` ` - не размечено;
- `x` - покрыто;
- `~` - покрыто частично;
- `-` - не входит в активный слой.

### `Scenario`

- формулируется как проверяемое поведение;
- пишется словами, а не именем тестового метода;
- должен быть независим от конкретной реализации тестов.

Хорошо:

- Конструктор по двум точкам создаёт прямую, проходящую через обе точки.
- `Intersect` возвращает `Parallel` для различных параллельных прямых.

Плохо:

- `Line2D_Intersect_Parallel_ReturnsParallel`
- Проверить пересечение.

### `Tests`

- здесь указываются ссылки на реальные тесты;
- допускается несколько ссылок на один сценарий;
- если тестов ещё нет, ячейка остаётся пустой.

Хорошо:

```md
[Line2DTests.cs](../../../Tests/SharedTests/Line2DTests.cs#L42)
```

или

```md
[Line2DTests.cs](../../../Tests/SharedTests/Line2DTests.cs#L42), [Line2DTests.cs](../../../Tests/SharedTests/Line2DTests.cs#L57)
```

## Как трактовать вырожденные входы

- сценарии с вырожденными объектами или заведомо некорректными входами не включаются в активное покрытие автоматически;
- если код считает такие случаи нарушением preconditions и не обязан стабильно обрабатывать их в `Release`, это не фиксируется как нормальный тестовый контракт;
- в coverage-документации такие случаи допустимо упоминать в `Gaps` или `Notes`, чтобы явно показать, что поведение намеренно не стандартизовано;
- если для такого случая позже появляется явный контракт API, его нужно перенести в таблицу `Scenarios` как обычный сценарий.

## Почему формат подходит для больших классов

Подходит, если:

- один класс разбивается на несколько тематических файлов;
- в одном файле держится только одна смысловая зона;
- не пытаться впихнуть весь API большого класса в одну таблицу.

Не подходит в лоб, если:

- сделать один файл на 100+ сценариев без тематического деления;
- смешать конструкторы, арифметику, геометрию, фабрики и ошибки в одну таблицу.

Практическое правило:

- до примерно 15-25 сценариев на файл формат читается хорошо;
- если сценариев становится больше, файл надо дробить ещё.
