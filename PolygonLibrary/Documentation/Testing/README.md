# Testing Documentation

Эта папка содержит документацию по покрытию тестами.

- [`ScenarioFormat.md`](ScenarioFormat.md) — зафиксированный шаблон оформления.
- [`DoubleGeometryMigrationOrder.md`](DoubleGeometryMigrationOrder.md) — порядок закрытия классов и текущий статус миграции.
- [`NewTestsLog.md`](NewTestsLog.md) — журнал новых тестовых файлов по уже закрытым классам.
- [`FundamentalTestReview.md`](FundamentalTestReview.md) — сводка по фундаментальным быстрым тестам: пропущенные сценарии, фактические падения и спорные места контракта.

Назначение:

- фиксировать, что именно должно быть протестировано;
- показывать, что уже покрыто существующими тестами;
- выявлять пробелы перед дописыванием новых тестов.

Текущий приоритет:

- в первую очередь раскладывается покрытие для конфигурации `double`;
- если существующий тест лежит в `SharedTests`, но релевантен и для `double`, это всё равно считается полезным источником покрытия;
- переход к другим числовым типам можно делать позже на той же структуре сценариев.
- алгоритмический слой (`Documentation/Testing/CoveragePlan/Algorithms`, `Tests/DoubleGeometry/Algorithms` и соответствующие legacy-источники) временно заморожен: его тесты и документацию пока не меняем;
- до отдельного решения работаем только с фундаментом: базовые объекты, линейная алгебра, базовая 2D/3D-геометрия и связанные с ними прямые контракты.
- после запуска быстрых фундаментальных тестов результат надо синхронизировать с `FundamentalTestReview.md`, не меняя в этом проходе production-код без отдельного решения.

Принципы оформления:

- один класс или одна небольшая сущность — одна папка;
- внутри папки есть `Index.md` и несколько небольших тематических файлов;
- в `Existing Tests` описывается не имя тестового метода, а словами, какой сценарий уже покрыт;
- один и тот же сценарий не должен дублироваться в нескольких местах без необходимости;
- основной рабочий формат сценариев — таблица с колонками `ID`, `Status`, `Scenario`, `Tests`;
- в колонке `Tests` указываются ссылки на тестовые файлы и строки, а не просто имена методов без контекста;
- все ссылки в `Documentation/Testing` пишутся относительными, без абсолютных путей к репозиторию;
- для больших классов сценарии надо разбивать на несколько тематических файлов, а не складывать всё в один документ.

Правило про вырожденные и заведомо некорректные входы:

- сценарии, нарушающие preconditions API, не входят в обязательный минимум покрытия по умолчанию;
- если библиотека в `Release` сознательно не валидирует такие входы ради производительности, это не считается gap-ом в тестировании;
- такие случаи можно упоминать в `Gaps` или `Notes`, но только чтобы явно показать, что поведение не закрепляется как публичный runtime-контракт;
- включать такие сценарии в обязательные тесты стоит только тогда, когда для них явно зафиксирован контракт уровня API.

Статусы покрытия:

- ` ` — не размечено;
- `x` — покрыто;
- `~` — покрыто частично;
- `-` — не входит в обязательный минимум.

Структура:

- `CoveragePlan/` — тематические планы покрытия по классам и сущностям.
