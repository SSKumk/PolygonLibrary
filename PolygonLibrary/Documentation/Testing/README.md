# Testing Documentation

Эта папка содержит документацию по покрытию тестами.

## Навигация

- [`ScenarioFormat.md`](ScenarioFormat.md)
  Объект: эталонный формат документов в `CoveragePlan`.
  Когда использовать: когда нужно создать новый coverage-файл или проверить, что существующий документ оформлен по принятому шаблону.

- [`DoubleGeometryMigrationOrder.md`](DoubleGeometryMigrationOrder.md)
  Объект: порядок закрытия классов и текущий статус миграции тестов `double`.
  Когда использовать: когда нужно понять, какой класс переносится сейчас, что уже закрыто и что остаётся в очереди.

- [`NewTestsLog.md`](NewTestsLog.md)
  Объект: журнал новых тестовых файлов по уже закрытым классам.
  Когда использовать: когда нужно быстро посмотреть, какие именно тесты были добавлены в новом слое и какую функциональность они покрывают.

- [`FundamentalTestReview.md`](FundamentalTestReview.md)
  Объект: сводка по быстрым фундаментальным тестам, пробелам и фактическим падениям.
  Когда использовать: когда нужно понять текущее качество базового слоя, увидеть реальные ошибки и не потерять спорные места контракта.

- [`CoveragePlan/`](./CoveragePlan/)
  Объект: тематические планы покрытия по классам и сущностям.
  Когда использовать: когда нужно детально смотреть сценарии, статусы покрытия и привязку к конкретным тестовым файлам.

Назначение:

- фиксировать, что именно должно быть протестировано;
- показывать, что уже покрыто существующими тестами;
- выявлять пробелы перед дописыванием новых тестов.

Coverage-документация фиксирует наблюдаемый текущий контракт и текущее состояние покрытия, а не желаемое будущее поведение, если оно отдельно не принято.

Текущий приоритет:

- в первую очередь раскладывается покрытие для конфигурации `double`;
- если существующий legacy-тест лежит в `Archive/SharedTests` или другом архивном слое, но релевантен и для `double`, это всё равно считается полезным источником покрытия;
- переход к другим числовым типам можно делать позже на той же структуре сценариев.
- геометрический алгоритмический слой (`GiftWrapping`, `Minkowski*` и подобные блоки в `Tests/DoubleGeometry/Algorithms`) по-прежнему двигается только отдельным решением;
- линейно-алгебраические алгоритмы низкого уровня входят в активный слой вместе с фундаментом: базовые объекты, линейная алгебра, базовая 2D/3D-геометрия и связанные с ними прямые контракты.
- после запуска быстрых фундаментальных тестов результат надо синхронизировать с `FundamentalTestReview.md`, не меняя в этом проходе production-код без отдельного решения.

Принципы оформления:

- один класс или одна небольшая сущность - одна папка;
- внутри папки есть `Index.md` и несколько небольших тематических файлов;
- в `Existing Tests` описывается не имя тестового метода, а словами, какой сценарий уже покрыт;
- один и тот же сценарий не должен дублироваться в нескольких местах без необходимости;
- основной рабочий формат сценариев - таблица с колонками `ID`, `Status`, `Scenario`, `Tests`;
- в колонке `Tests` указываются ссылки на тестовые файлы и строки, а не просто имена методов без контекста;
- все ссылки в `Documentation/Testing` пишутся относительными, без абсолютных путей к репозиторию;
- для больших классов сценарии надо разбивать на несколько тематических файлов, а не складывать всё в один документ.

Правило про вырожденные и заведомо некорректные входы:

- сценарии, нарушающие preconditions API, не входят в активный слой покрытия по умолчанию;
- если библиотека в `Release` сознательно не валидирует такие входы ради производительности, это не считается gap-ом в тестировании;
- такие случаи можно упоминать в `Gaps` или `Notes`, но только чтобы явно показать, что поведение не закрепляется как публичный runtime-контракт;
- включать такие сценарии в активные тесты текущего слоя стоит только тогда, когда для них явно зафиксирован контракт уровня API.

Статусы покрытия:

- ` ` - не размечено;
- `x` - покрыто;
- `~` - покрыто частично;
- `-` - не входит в активный слой.

Структура:

- `CoveragePlan/` - тематические планы покрытия по классам и сущностям.
