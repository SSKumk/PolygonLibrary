# Build And Test Workflow

Этот файл фиксирует рабочие правила запуска сборок, тестов и временных research-runner'ов.

Общее правило: для одного проекта не запускать несколько процессов, которые одновременно используют его `bin/obj`.

## Базовое правило

- Для одного `.csproj` в один момент времени допускается только один активный `dotnet build`, `dotnet test` или `dotnet run`.
- Не запускать параллельно:
  - два `dotnet test` на `Tests/Tests.csproj`;
  - `dotnet build` и `dotnet test` на `Tests/Tests.csproj`;
  - `dotnet run` и `dotnet build` на одном и том же проекте;
  - обычные CLI-сборки параллельно с `dotnet watch` или continuous testing на том же проекте.

## Почему это важно

- В текущем рабочем окружении параллельные сборки и тесты регулярно упираются в file locks на `Tests.dll` и соседних артефактах.
- Такие падения не являются содержательным сигналом о проблеме в коде; это проблема workflow.
- Поэтому параллельные build/test прогоны считаются неверным способом работы с репозиторием.

## Практические правила

- Сначала дождаться завершения текущего `dotnet`-процесса, потом запускать следующий.
- Если после `dotnet test` следующий `dotnet build` ловит временную блокировку артефактов, просто повторить команду после завершения testhost.
- Для локальной проверки предпочитать узкие прогоны:
  - `dotnet test Tests/Tests.csproj --filter ...`
  - а не несколько широких прогонов одновременно.
- Research-runner'ы в `Sandbox` запускать только по одному и после завершения исследования убирать из `Sandbox`.

## Что не фиксируется как рабочий режим

- Параллельные сборки одного тестового проекта ради экономии времени.
- Одновременный запуск нескольких research-runner'ов через `Sandbox`.
- Фоновый `dotnet watch`, если параллельно руками гоняются `build/test/run` того же проекта.
