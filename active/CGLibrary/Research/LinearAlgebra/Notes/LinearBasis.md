## Назначение

`LinearBasis` представляет ортонормированный базис линейного подпространства в объёме `SpaceDim`.

Тип отвечает не за произвольный набор независимых векторов, а именно за уже ортонормированное представление, пригодное для:

- проектирования на подпространство;
- проектирования на ортогональное дополнение;
- перехода между вектором и его координатами в базисе;
- численно устойчивого достраивания нового ортогонального направления.

`LinearBasisMutable` использует то же представление, но допускает инкрементальное изменение базиса.

## Представление

Базис хранится не как отдельная прямоугольная матрица `k x d`, а как первые `k = SubSpaceDim` строк полного ортогонального оператора размера `d x d`.

То есть внутренняя матрица `_Basis` устроена так:

```text
_Basis =
[ b_1 ]
[ ... ]
[ b_k ]
[ c_1 ]
[ ... ]
[ c_(d-k) ]
```

где:

- `b_i` образуют активный ортонормированный базис подпространства;
- `c_j` образуют ортонормированный базис ортогонального дополнения.

Это представление важно по двум причинам:

- операции проекции и перехода к координатам выражаются напрямую через строки `_Basis`;
- инкрементальные QR/LQ-обновления можно применять к полному ортогональному оператору без смены модели хранения.

## Базовые формулы

Пусть `B` это матрица из первых `k` строк `_Basis`.

Тогда:

- координаты вектора `v` в базисе подпространства равны `B v`;
- восстановление по координатам `a` равно `B^T a`;
- ортогональный проектор на подпространство равен `B^T B`;
- проектор на ортогональное дополнение равен `I - B^T B`.

Поскольку строки `B` ортонормированы, здесь не требуется решать дополнительную систему или инвертировать матрицу Грама.

## Инварианты

Для корректной работы типа должны выполняться следующие инварианты:

- первые `SubSpaceDim` строк `_Basis` ортонормированы;
- все строки `_Basis` вместе образуют полный ортонормированный оператор;
- `0 <= SubSpaceDim <= SpaceDim`;
- кэш `_projMatrix`, если он построен, соответствует текущему активному базису.

Именно поэтому конструкторы не просто принимают матрицу, а нормализуют вход к этому представлению.

## Почему полная ортогональная матрица

На первый взгляд кажется, что достаточно хранить только активные строки базиса. В библиотеке выбран более сильный инвариант: хранить сразу весь ортогональный оператор.

Это даёт:

- дешёвый доступ к ортогональному дополнению;
- естественную связь с QR/LQ-инкрементальными обновлениями;
- единое представление для immutable- и mutable-вариантов;
- меньше специальных веток в низкоуровневых алгоритмах.

Цена такого решения очевидна: хранится `d x d` матрица вместо `k x d`. Для данного слоя библиотеки это признано приемлемым обменом памяти на простоту и устойчивость алгоритмов.

## Ортогонализация

Метод `Orthonormalize(Vector v)` не модифицирует базис. Он отвечает на более узкий вопрос: какой новый unit-вектор нужно добавить к текущему подпространству, чтобы расширить его направлением `v`.

Исторически метод использовал projector-based схему

```text
v - B^T (B v),
```

но production-реализация переведена на `LQ`-based update полного ортогонального оператора. Причина: на почти зависимых входах с большой компонентой в `span(B)` projector-based формула страдает от катастрофического вычитания.

Подробности и минимально воспроизводимое исследование вынесены отдельно в [`OrthonormalizeStability.md`](./OrthonormalizeStability.md).

## Как читать API

Если нужно быстро понять слой `LinearBasis`, удобно держать такую схему:

- `ProjectVectorToSubSpace` и `ProjectVectorToSubSpaceCoordinates` работают через активные строки базиса;
- `ProjectVectorToOrthogonalComplement` использует проектор на дополнение;
- `Orthonormalize` вычисляет кандидат на новый ортогональный вектор, не меняя сам объект;
- `LinearBasisMutable` добавляет к этому представлению операции инкрементального роста.

Для деталей низкоуровневых `QR/LQ`-обновлений см. соседнюю заметку про Householder-разложения.
